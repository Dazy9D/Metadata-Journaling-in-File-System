# VSFS Metadata Journaling

A term project that adds **metadata journaling** to a small VSFS-like file system so that metadata updates become **crash-consistent**.

The project works directly on a static, pre-built disk image (`vsfs.img`). The program `journal.c` edits that image in place: it first *logs* metadata changes to an on-disk journal (`create`), and later *applies* the committed changes to their real locations (`install`).

---


## Overview

Metadata journaling is a write-ahead logging technique. Instead of updating several metadata blocks in place (and risking an inconsistent image if a crash happens midway), the update is written to a journal first and sealed with a commit record. Only after that is it copied to its home location.

This project implements two operations:

| Command | What it does |
|---|---|
| `./journal create <name>` | Logs the metadata changes for a new file as **one committed transaction** in the journal. Nothing in the real metadata is modified. |
| `./journal install` | Replays every committed transaction to the home blocks, then **clears the journal**. |

Only **metadata** is journaled (bitmap blocks, inode table blocks, directory blocks). File data is not.

## Disk Layout

- **Block size:** 4 KB
- **Total blocks:** 85

| Component | Blocks |
|---|---|
| Superblock | 1 |
| Journal | 16 |
| Inode Bitmap | 1 |
| Data Bitmap | 1 |
| Inode Table | 2 |
| Data Blocks | 64 |

Regions are laid out in the order listed above. The superblock stores the exact block indices (`journal_block`, `inode_bitmap`, `data_bitmap`, `inode_start`, `data_start`), so read them from there rather than hard-coding them.

A freshly created image contains:

- a single inode for the root directory `/` with `inum = 0`,
- the first data block holding the root directory's **directory entries**,
- inode and data bitmaps updated accordingly,
- an **empty** journal.

## Build and Run

Build everything:

```bash
make all
```

This builds `mkfs`, `validator`, and `journal` from the sources.

Create a fresh disk image:

```bash
./mkfs                # produces vsfs.img
./mkfs <path>         # custom output path
```

Run the whole build and test cycle in one shot:

```bash
make test
```

`make test` runs: `mkfs` → `validator` → `journal create hello.txt` → `validator` → `journal install` → `validator`.

Clean up build artifacts and the image:

```bash
make clean
```

This removes `mkfs`, `validator`, `journal`, and `vsfs.img`.

## Commands

### `./journal create <name>`

Creates a file entry **by logging metadata only**.

It must:

1. Initialize the journal if it does not exist.
2. Read existing metadata to decide what would change:
   - find a free inode in the **inode bitmap**,
   - choose a free directory entry slot in the **root directory**.
3. Compute the *new versions* of the affected metadata blocks **in memory** (not on disk yet).
4. Append **one transaction** to the journal:
   - one **DATA** record for each modified metadata block (inode bitmap, inode table block, root directory data block),
   - followed by a **COMMIT** record.
5. Write changes **only** to the journal (and its header).

The inode bitmap, inode table, and directory blocks must **not** be modified in their home locations during `create`.

**Result:** the "real" metadata on the disk image still shows the old state, while the journal holds a committed transaction describing the pending updates.

Example:

```bash
./journal create hello.txt
```

### `./journal install`

Applies committed journaled updates to their home locations and then clears the journal.

It must:

1. Return a **failure** if the journal does not exist.
2. Read and parse the journal sequentially.
3. For each transaction that has a **COMMIT** record, replay every logged DATA record by writing its block image to its target home block number.
4. After replaying all committed transactions, **clear (checkpoint)** the journal so it is empty again.

Transactions without a valid, fully readable COMMIT record are not replayed.

## Journal Design

The journal is 16 blocks long and is treated as an **append-only byte array**:

```
[ journal_header ][ record ][ record ][ record ] ...
```

### Journal header (fixed at offset 0)

```c
#define JOURNAL_MAGIC 0x4A524E4C

struct journal_header {
    uint32_t magic;         // store JOURNAL_MAGIC
    uint32_t nbytes_used;   // total bytes currently used
};
```

- `magic` identifies a journal header (the characters `JRNL` stored in a 4-byte field).
- `nbytes_used` tells you where the next append goes. It **must be updated** each time an entry is appended or removed.
- An **empty journal** means `nbytes_used == sizeof(journal_header)`.

### Record header

Every record starts with a header that gives its type and its size, so the parser knows how far to advance to reach the next record.

```c
struct rec_header {
    uint16_t type;   // REC_DATA or REC_COMMIT
    uint16_t size;   // total size of this record in bytes
};
```

### DATA record

A DATA record holds **one full file system block image** to be written to a particular home block.

```c
struct data_record {
    struct rec_header hdr;   // type = REC_DATA
    uint32_t block_no;       // home block number on disk
    uint8_t  data[4096];     // full block image
};
```

- Record size = size of the header + size of `block_no` + block size.
- **Whole blocks** are logged. For example, adding a directory entry means logging the entire updated root directory block, not just the new entry.
- Only **metadata blocks** are logged (bitmap, inode table, and directory blocks).

### COMMIT record

A COMMIT record seals one transaction.

```c
struct commit_record {
    struct rec_header hdr;   // type = REC_COMMIT
};
```

- All DATA records since the previous COMMIT (or since the start of the journal) belong to the current transaction.
- A transaction is valid **only if** its COMMIT record is present and fully readable.

## File System Data Structures

### Superblock (128 bytes)

```c
#define FS_MAGIC 0x56534653  // "VSFS"

struct superblock {
    uint32_t magic;            // FS magic number
    uint32_t block_size;       // 4096
    uint32_t total_blocks;     // total blocks in FS
    uint32_t inode_count;      // total inodes

    uint32_t journal_block;    // block index of journal
    uint32_t inode_bitmap;     // inode bitmap block
    uint32_t data_bitmap;      // data bitmap block
    uint32_t inode_start;      // first inode block
    uint32_t data_start;       // first data block

    uint8_t  _pad[128 - 9*4];  // padding to 128 bytes
};
```

### Inode (128 bytes)

```c
struct inode {
    uint16_t type;             // 0=free, 1=file, 2=dir
    uint16_t links;            // link count
    uint32_t size;             // file size in bytes

    uint32_t direct[8];        // 8 direct block pointers

    uint32_t ctime;            // creation time
    uint32_t mtime;            // modification time

    uint8_t  _pad[128 - (2+2+4 + 8*4 + 4+4)];
};
```

### Bitmaps

The inode bitmap and data bitmap are byte arrays with 4096 elements each.

### Directory entry (32 bytes)

```c
#define NAME_LEN 28

struct dirent {
    uint32_t inode;            // inode number (0 = unused)
    char     name[NAME_LEN];   // null-terminated if shorter
};
```

## Operational Constraints

- Multiple transactions may be appended to the journal until it fills up.
- If there is not enough space to append a **full** new transaction, the command must **refuse** and instruct the user to run `./journal install`.
- Only metadata journaling is required.

## Validating the File System

Use the provided validator to check consistency at any point:

```bash
./validator          # checks vsfs.img
./validator <path>   # checks a custom image
```

Run it once on the freshly created image, then again after every `create` and `install`. A consistent image satisfies:

- the inode bitmap matches which inode slots are in use,
- directory entries reference allocated inodes,
- there are no invalid block numbers, no duplicates, and no dangling references.

## Typical Session

```bash
make all
./mkfs
./validator            # confirm the fresh image is consistent
./journal create foo.txt
./validator            # journal shows 1 committed transaction, disk metadata still old
./journal install
./validator            # foo.txt is now really on disk, journal is empty again
```

## Debugging Tips

- Use a **hex inspector** (graphical or command-line) to open `vsfs.img` and examine the journal and metadata blocks directly.
- Map the on-disk structures onto the C structs above and traverse them with struct pointers rather than manual byte arithmetic.
- After `create`, the home metadata blocks should be byte-for-byte unchanged; only the journal region should differ.
- After `install`, the journal header should show an empty journal (`nbytes_used == sizeof(journal_header)`).
